# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Project 25 — a single-page personal life-dashboard web app (goals, habits, finance, fitness, Valorant tracking, checklists, countdowns, mantras). See `README.md` for the full feature/architecture writeup (data model, persistence internals, Supabase Edge Functions, Valorant local-script setup) — it's kept accurate and detailed; read it before making non-trivial changes rather than re-deriving structure from the code.

## No build step

Plain HTML/CSS/JS, no npm, no bundler, no framework.

- **Run/test the app**: open `index.html` directly in a browser, or run `node scripts/serve.mjs` and open `http://localhost:8025` (plain `node:http` static server, no install). There is still no build, lint, or test command in this repo. Session music is the one feature that needs the served form — YouTube refuses to embed its player into a `file://` page (error 153), see README's "Session music". That section also covers the two playback modes (`state.sessionMusic.mode`): the in-app iframe player can't see a Premium account, because a cross-site frame only gets YouTube's cookies when the browser allows them there — `external` mode hands the playlist to YouTube Music instead. Don't try to "fix" the ads inside the embed; the mode picker is the fix.
- **Scripts in `scripts/`** (Valorant helpers, backup): plain Node.js built-ins only, run directly with `node scripts/<file>.mjs` — no `npm install` anywhere in the project.
- Supabase Edge Functions live in `supabase/functions/*/index.ts`, deployed via the Supabase CLI (not part of this repo's build).

## Architecture essentials

- `index.html` loads a **fixed sequence** of `<script>` tags from `js/` — order matters, later files reference functions/globals defined in earlier ones:
  ```
  pin.js → core.js → persistence.js → protecteddays.js → nav.js → goals.js → habits.js →
  countdowns.js → settings.js → backups.js → mantras.js → motivation.js → music.js →
  checklists.js → notes.js → scratch.js → finance.js → wishlist.js → jobs.js → fitness.js →
  valorant.js → clock.js → calendar.js → tft.js → board.js → insights.js → main.js
  ```
  **`sw.js` precaches this same list by hand** (`SHELL_ASSETS`). Adding a `js/` file without adding it there installs fine and then boots offline with that tab's render function undefined — add the name *and* bump `SHELL_CACHE`, or the old cache keeps serving the old `index.html`.
- **`js/pin.js` is the front door and loads before everything else** (`#pinGate` at the top of `index.html`, its `<script>` tag directly beneath it rather than with the rest at the end of the body). Two PINs, two roles: owner gets everything, guest gets everything except the scratch page. Read README's "PIN gate" before touching it. **It is a soft gate, not authentication** — the file ships to the browser and the shared row stays unauthenticated whichever PIN was typed — so don't put anything behind it that would be a real problem to lose, and equally don't "harden" it into something it can't be in a repo with no build step. Six rules. It **depends on nothing**, not `el()`, not `state`, because it must answer before the boot order can matter. The boot **waits** on it: `js/main.js` runs `load()` off `p25GateReady`, since the role decides which resources may be *fetched* — `loadScratchData()` returns immediately for a guest, so a guest's browser never holds the scratch text at all, and hiding the way in while it sat in memory would be a curtain rather than a door. **Unknown fails closed** (`p25IsGuest()` is true for an undecided role, and the three scratch guards ask `p25IsOwner()` so an absent pin.js loses the easter egg instead of leaking it). **The role is never passed in from outside** — there is no `p25SetRole()` and `unlock()` isn't exported, or a bookmarklet could promote itself. It lives in **`sessionStorage`** (closing the tab re-locks; a reload doesn't, because re-typing after an accidental refresh mid-edit teaches you to hate the gate), while the wrong-PIN lockout is the one thing in `localStorage`, so a reload can't be the way past it. And the Settings → Data *Lock screen* card **must never name what a guest is missing** — "a restricted version" is the wording, because the scratch page's whole design is that nothing in the UI admits it exists.
- All modules share one global `state` object (shape defined/defaulted in `core.js` / `persistence.js:applyLoadedState()`) and small globals (`el()`, `uid()`, `escapeHtml()`, date helpers). No modules, no per-file scoping, no virtual DOM — each tab's `render*()` rebuilds that section's `innerHTML` from `state` on every change, and `save()` runs after essentially every mutation.
- One file per feature tab (`goals.js`, `habits.js`, `finance.js`, `fitness.js`, `valorant.js`, `tft.js`, `checklists.js`, `notes.js`, `countdowns.js`, `calendar.js`, `mantras.js`, `clock.js`, `wishlist.js`, `jobs.js`, `backups.js`, `settings.js`, `protecteddays.js`), each owning its own render function and DOM listeners — no central router.
- **`js/settings.js` used to be called `insights.js`** and held no analytics at all — it is the Settings renderer plus `applyTabOrder()`/`applyTabIcons()`/`applyTabVisibility()`/`visibleNavItems()`/`showSettingsSubTab()`. The name now belongs to the real Insights tab, so don't reintroduce the old one.
- **The access log is the only thing in this app that writes without the user doing anything** (`js/access.js`, Settings → Data). It records what device the app was opened on and roughly where from, because the shared row is unauthenticated and nothing else could answer "has anyone but me opened this?". Read README's "Access log" before touching it. Seven rules. It logs **sessions, not page loads**: an open matching the newest entry's device *and* network within `ACCESS_SESSION_GAP_MS` bumps `lastAt`/`visits` instead of appending, or the list is a wall of identical rows and the one new device is invisible in it. It rides the **shared blob** (a plain top-level `state.access` key — the rest-destructure carries it), so `ACCESS_LOG_CAP` is load-bearing, not cosmetic. **A bump usually costs no write**: because this is an unattended write and the row has optimistic-concurrency detection, only a new entry or a bump older than `ACCESS_BUMP_MIN_MS` calls `save()` — anything smaller stays in memory and rides the next ordinary save, or a phone opening the app hands the laptop a conflict banner it did nothing to earn. Location is **IP-level, never the Geolocation API**, which prompts — a permission dialog on every app open to fill a log nobody asked to see is the worse trade; the three lookup services are keyless and CORS-open, the `api.metatft.com` ruling, so the browser calls them directly and no Edge Function is involved. Their hosts **must stay in `sw.js`'s `LIVE_DATA_HOSTS`**, and for a sharper reason than the rest of that list: the cross-origin branch is cache-*first*, so a cached lookup pins the answer to whatever network the app was first opened on and every later session claims that place. The geo result arrives *after* the device half is recorded, so **a different IP un-bumps and splits** (`accessBumpUndo`) — that split is what makes the log answer "where" rather than showing one merged row per device. And **both switches and Clear stay**, because this stores the user's own IP in that same unauthenticated row; don't quietly drop them to simplify the card. Note the browser *version* is deliberately outside the merge fingerprint — a background update mid-session must not split one sitting in two.
- **The Insights tab is read-only by contract** (`js/insights.js`, loaded last because it reads across every other file). It never mutates `state` and never calls `save()`, which is what keeps it outside every rule in "Data safety" below — no new state key, no `applyLoadedState()` default, no `doSave()` change. Three rules keep it honest. **Every figure comes from the owning tab's own helper** (`totalExp()`, `calcStreak()`, `dailiesOverallProgress()`, `moneyGoalSaved()`, `tftSortedEntries()`, `getFitnessTier()`, …) rather than being re-derived — that's what stops Insights and its source tab disagreeing about the same number, so a figure needing new maths goes in the owning file and gets called from here. **`insGoTo()` reuses nav.js's own click ladder** (`item.click()`) instead of duplicating the per-tab teardown/setup it does, and applies the sub-tab *after* that click, never instead of it — the ladder resets Finance to `accounts` and Games to `state.games.active`, so anything set first is immediately overwritten. That `showGameSubTab()` call is the one write the tab causes, and it is the same one clicking that sub-nav already makes. And `insSparkline()` is the only chart primitive here that isn't welded to one dataset: a fixed `0 0 100 28` viewBox with `preserveAspectRatio="none"` plus `vector-effect="non-scaling-stroke"` buys that generality by giving up the width measurement, `ResizeObserver` and `k` scale factor the four real charts need — don't "upgrade" it into another copy of them, because summarise-then-deep-link is the whole design and the real chart already lives one click away.
- **The Time tab holds three panes, and Calendar is the only one that isn't local** (`js/calendar.js`, `#timetab-calendar`, revealed by `showTimeSubTab()` in `js/countdowns.js` which owns `#view-time`). It's a read-only Google Calendar agenda served by the `google-calendar` Edge Function — `calendar.readonly`, so nothing here can alter a real event. Read README's "Google Calendar" section before touching it. The rules that hold it up: **the fetched events never touch `state`** — they live in a module-level `calEvents`, the same ruling as `state.valorant.live`, because `doSave()`'s rest-destructure would carry them into the shared blob that is re-uploaded in full on every save from every tab, for data that is stale within the hour; `state.calendar` is therefore preferences only, and the accepted cost is that **there is no offline agenda** — don't "fix" that by caching events into `state`. `singleEvents=true` on the server's events call is load-bearing (without it a weekly standup returns once with an `RRULE` and this app would have to expand recurrence itself), and both ends append `T00:00:00` to an all-day `start.date` because parsing that bare date reads it as UTC and lands on the wrong local day. The **bubbles** (`#calBubbleStack`) show the **next `bubbleCount` events on the calendar**, whatever they are, within `bubbleDays` (default 7, clamped to `lookaheadDays`) — all-day events included, matched on their *day* since their `startMs` is midnight. Ahead of them sits the **"now until" card** (`calNowEvent()`) for the event you're currently in — "now until 3:00 PM · 25m left", `.cal-bubble.is-now`. Four rules: it is **extra, not one of the `bubbleCount` slots** (that count means "things coming up", so answering it with the meeting you're already in would displace the card it was asked for); **timed events only**, since an all-day event runs midnight to midnight and today's is already carried by the ordinary card's plain "now"; **at most one, the soonest-ending**, because overlapping meetings are real and "when am I free" is the question the card answers; and it's a `source:'now'` **copy**, never the `calEvents` record, which the agenda pane renders from. The end time is parsed client-side by `calEventEndMs()` (the Edge Function passes `endIso` through without a millisecond twin), appending the same `T00:00:00` for an all-day date and falling back to the start, so a bad end reads as already-finished instead of `NaN`. No dedupe is needed — `startMs >= now` is exactly the test that drops the events this card is built from. **`state.countdowns` can join the same stack** (`bubbleCountdowns`): `countdownBubbleEvents()` maps a countdown onto the same event record rather than giving it a parallel path, `calBubbleCandidates()` merges and re-sorts so the two interleave by date, and such a card shows ⏳ and deep-links to *Countdowns*, not Calendar. That also means the bubble works with **no Supabase at all** — countdowns are local, so `maybeShowCalendarBubble()` skips the fetch entirely in that mode. The agenda fetch window is `calAgendaDays()` = `max(lookaheadDays, bubbleDays)`, never `lookaheadDays` alone, or a 30-day horizon shows countdowns that far out while calendar events stop at whatever was fetched. The horizon is **calendar days** via countdowns.js's `daysLeft()`, never `now + N×24h`: a millisecond horizon cuts off mid-way through the last day, so the same meeting was in or out depending on the clock while the bubble called it "in 7 days" either way. It fires once per page load from `maybeShowCalendarBubble()` in `renderAll()` — the same no-op-unless-needed slot as `maybeSyncPinterestCategories()` — and its fetch is async so it never delays `hideLoadScreen()`; it must stay a **body-level sibling of `.main`** (a `.view` would hide it whenever Time wasn't active, the `#valItemPreviewOverlay` reason) at **`z-index:920`**: above the mobile sticky sidebar (40), below the scratch mode (950) and the 1000 modal tier, because a notification must never cover a dialog — and it sits *later* in the DOM than `#scratchOverlay`, so the number is what keeps it under. It's pinned **top right under the navbar** off `--nav-h` (js/nav.js's measured bar height, live via ResizeObserver, and exactly 0 on desktop where the nav is a left sidebar) — don't add `env(safe-area-inset-top)` on top of it, since that offsetHeight already contains the inset. The stack is the always-present `aria-live` container and owns the fixed positioning (`pointer-events:none`, `auto` on the cards, or it eats clicks in the gaps); cards are rebuilt per show, so handlers are **delegated from the stack**. The **whole card** is the click target (no View button) and reuses nav.js's click ladder, applying the sub-tab *after* `item.click()`, never instead of it, exactly as `insGoTo()` does — the ✕ must keep its `stopPropagation()`, or dismissing also navigates. Cards animate OUT as well as in; the removal is on a **timer, never `animationend`**, because the animation is off under `prefers-reduced-motion` and that event would never fire — and `hideCalBubbles()` (animated) has a synchronous twin `clearCalBubbles()` for `showCalBubbles()`'s reset, which can't animate or a refresh would show both batches. A click anywhere outside the stack clears it, via a listener added on show and removed on hide that must stay in the **capture** phase — in the bubble phase the ✕ handler has already detached the card, so `closest('#calBubbleStack')` finds nothing and dismissing one card takes the whole stack down. ✕ is **session-only and records nothing** — persisting dismissals silenced an event for the whole seven-day horizon, and the stack is built once per page load anyway, so removing the card already is “gone for this session”; don't reintroduce a `dismissed` list. It stays `role="status"`, not `role="button"`: being announced on arrival is the point, so `tabindex` + Enter/Space carry the keyboard path instead. The bubble is **coloured by the calendar the event is on**: the per-calendar `backgroundColor` is attached server-side (the client's calendar list isn't fetched until the pane is opened, and the bubble fires before that), and `calAccentFor()` splits it into two CSS variables — `--cal-accent` raw for the **spine**/rings/chip-wash, `--cal-accent-ink` contrast-corrected for anything that becomes text (the countdown line, the icon glyph). Don't collapse them into one: correcting a single shared value crushes pale calendar colours to mud, and using the raw one for text fails AA. The accent is a 4px spine and a neutral hairline border, never a coloured border — half of Google's palette is pale, so a 1px line in it is invisible on the very card whose only reason to be coloured is telling two calendars apart; the same spine at 3px runs down each `.cal-row`, and the picker chips carry the calendar's dot on or off, so the colour means the same thing in all three places. The picker's selected chip is a wash plus `--cal-ink-text`, never `--cal-ink` behind white — that was ~1.6:1 on "Banana", the same bug the bubble's correction exists for. Verified ≥4.5:1 across all four themes and Google's full palette. Finally the calendar picker's chips are `.cal-chip` and deliberately **not** `.finance-subnav-btn`: `showTimeSubTab()` strips `.active` off every `#view-time .finance-subnav-btn`, which would blank them on each sub-tab switch.
- **The Games tab holds two games, not one** (`#view-games` in `index.html`). An outer `.finance-subnav` strip picks Valorant or TFT (`showGameSubTab()` in `js/tft.js`, panes `#gametab-valorant` / `#gametab-tft`); Valorant keeps its own Live/Shop/RR `.unit-toggle` underneath, unchanged. Three things to know: the game choice **persists** in `state.games.active` (unlike the Time/Finance sub-navs, which reset on entry — those are two views of one concern, these are two different games, and landing on Valorant every time would start the Live Match poll for someone who only plays TFT); `state.games.active === 'valorant'` is therefore a clause in `syncValLivePolling()`, which is what stops the poll when you switch *within* the tab rather than leaving it; and the tab key is `games`, so `#valItemPreviewOverlay` must stay a **sibling** of `#view-games` (it renders at body level) and the `#view-games`-scoped CSS carries the focus-ring guarantee for both games.
- **TFT auto-syncs from MetaTFT, and that is *not* a contradiction of the local-only Valorant rule** (`tftSync()` in `js/tft.js`). The Valorant tooling is local-only because it replays the user's own Riot session against Riot's endpoints; MetaTFT is a third party serving its own index of public profiles, and its `public/` endpoints send permissive CORS, so the browser calls them directly — no helper, no Edge Function, no key. Read README's "TFT rank sync" before touching it. Five standing rules: **only the current set** is imported (LP resets between sets, so mixing them draws a cliff that never happened); pairing a match's placement to a rating point is deliberately conservative (nearest point at/after the match within 45 min, never reassigned once claimed) because a mis-paired placement corrupts the stats invisibly while a missing one is merely absent; `srcKey` is what makes re-syncing idempotent, and hand-typed rows have none, so a sync can never touch them; an imported row is **stamped with the account it came from** (`acct`) and a sync for a different Riot ID/region purges the other account's imported rows *before* merging — one chart, no per-account switch, so two ladders on one line draw a climb that never happened; that purge is only safe because placements are carried across it by `srcKey` (a row too old to re-pair would otherwise come back without one), because a failed `rating_changes` call is passed as **`null`, not `[]`** so a blip can't read as "no games" and empty the log, and because it never touches hand-typed rows; and **manual entry stays** — it's an undocumented API that can break without notice, so a failed sync must never leave you with no way to record a game. Note the region field is the *platform* code (`sg2`), not the routing region in MetaTFT's own URLs (`sea`). The pace line races **`state.tft.season.endDate`**, not a per-target date, because rank resets when a set ends — `season.set` is detected from `tft_set_name` on sync and the end date is typed once, since Riot only announces it in patch notes (MetaTFT and the set tables were both checked and neither publishes it); a detected set change clears the date so a rollover can't leave a stale deadline skewing the maths. The HenrikDev key in `state.valorant.apiKey` is Valorant-only and Riot's official TFT API needs a key that expires every 24h — neither is a route back here. Rank power is `tierIndex*100 + LP` (the RR chart's `valOf()` trick); Master/Grandmaster/Challenger deliberately **share one step**, because in TFT they're one LP pool and GM/Challenger are ladder cutoffs rather than LP thresholds. Don't "fix" that by giving them their own steps — it would rank Master 400 LP above Challenger 0 LP. `tftSortedEntries()` is the only place ordering happens (date, then `createdAt` as the same-day tiebreak) and the only place bad tier keys are filtered; bypassing it lets one hand-edited record NaN the whole chart.
- **The TFT Live Lobby is local-helper-backed, and that is not the Valorant ruling repeating itself** (`scripts/tft-live.mjs`, `POST /tft-live` on `valorant-local-server.mjs`, the LIVE LOBBY section of `js/tft.js`). It shows the eight players in the current game and the highest rank each has ever held. Read README's "TFT live lobby" before touching it. The Valorant tooling is local because Riot's fraud detection rejects a *session replay* from a cloud IP; this is local for a plain mechanical reason — the roster comes from the League/TFT client's own loopback API, which serves a self-signed cert and keeps its port and password in a `lockfile` only a same-machine process can read, so no page can call it from any host. Every call it makes is a read-only GET and nothing authenticates as anybody, so don't import the anti-detection reasoning here; equally, don't "fix" the helper dependency by moving it to an Edge Function, which would be a cloud service asking a machine it can't see for a lockfile. The route rides on the **Valorant** helper on purpose: one port, one token, one "helper not running" banner for a bridge the user already runs — it touches no Valorant session file. Six standing rules. **The puuid bridge is load-bearing**: the client reports UUID-form puuids and MetaTFT indexes the *encrypted* puuid, two identifiers with no conversion between them, so the roster is resolved to Riot IDs via the client's own `/lol-summoner/v2/summoners/puuid/` and looked up by Riot ID — `lookup_by_puuid` exists and 404s for every player in a lobby, so collapsing the chain into it silently empties the card. **Memory-only**, the `state.valorant.live` ruling exactly: `state.tft.lobby` is preferences, the roster lives in `tftLobbyState` and in the helper's memory, and a panel that polls every few seconds must never reach `doSave()`'s shared-row re-upload. It has its **own sub-tab** (`showTftSubTab()`, `Rank | Live Lobby`, panes `#tftSubtabRank` / `#tftSubtabLobby`) and `tftActiveSubtab === 'lobby'` is a clause in `tftLobbyVisible()` — switching to Rank hides the panel as surely as leaving the tab does, and that clause is what stops the poll then, the same role `state.valorant.activeSubtab === 'live'` plays for Live Match. That sub-tab is a module-level variable and **resets to Rank on entry**, unlike the Games strip one level up which persists: two views of one game rather than two games, and the reset is also what stops opening the tab from starting the poll on its own. `showGameSubTab()` therefore calls `showTftSubTab('rank')` *before* `renderTft()`, or the lobby pane still counts as visible from the previous visit and the poll starts for a pane about to be hidden; `showTftSubTab()` also redraws the chart when it reveals Rank, since a `display:none` container measures 0. The gate is **`gameMode: 'TFT'`, never a queue-id allowlist**, or the card goes blank for the first week of every new mode Riot ships. **The gap to peak is quoted in the unit that is true at that distance** (`tftLobbyGapText()`) — tiers across tiers, divisions within a tier, LP only within one division: `tftValue()` is rank *power* where a step is a division, so subtracting two and calling it LP describes a 1640-LP loss that cannot happen (this is also why the apex tiers, sharing one step, correctly fall through to the LP branch). **`client_closed` is a state, not a fault** — it is what the helper says whenever the game isn't open, which is most of the time, so it keeps the idle cadence and collapses the card to one line instead of backing off to a minute and looking broken the moment you finally launch; every empty state is one line for the same reason, since this card sits above the rank summary. And **a failed rank lookup is never cached** (the roster is memoized per `gameId`, ranks for 10 minutes), or one blip leaves a row blank for the rest of the game. `state.tft.lobby` is defaulted in **`core.js` as well as `applyLoadedState()`**, the `games.active` exception: `syncTftLobbyPolling()` reads it from a `visibilitychange` listener that can fire before a load finishes.
- **The local helper's lifetime can be tied to the Riot client, and that is opt-in** (`scripts/local-helper-watch.mjs` + `.vbs`). It polls the process list and runs `valorant-local-server.mjs` only while `RiotClientServices.exe` / `LeagueClient.exe` / `TFTClient.exe` / Valorant is up — it's what you put in `shell:startup` *instead of* `valorant-local-server.vbs`, not alongside it. Four rules. **Starting is immediate, stopping needs two consecutive misses**, because the Riot Client really does vanish and return while handing off to a game and a single miss would kill the helper exactly when the lobby card is about to need it. **A failed process read returns `null`, never `false`** — "don't know" must not be actioned as "nothing is running", the same shape as the `rating_changes` `null`-not-`[]` rule above. It **never touches a server it didn't start**: it checks the port before spawning and only ever kills its own child, so it can't disturb a hand-started helper, and it kills that child on exit so a dead watcher can't orphan the thing it exists to manage. And the **cost is real and must stay documented** — Check Store / Add Account / Check Owned Skins need only a saved cookie and work with no game running, so under the watcher those buttons are dead while Riot is closed; the always-on `.vbs` remains the answer for anyone who wants them. The scheduled `valorant-check-store.mjs` is a separate process and is unaffected either way.
- **The local helper can be switched on and off from Settings, and the two directions are not symmetrical** (`POST /shutdown` on `valorant-local-server.mjs`, `scripts/helper-protocol.mjs`, `renderValHelperPower()` in `js/valorant.js`). Stop is an ordinary token-gated request; **Start cannot be one**, because by then nothing is listening — it hands off to a registered `p25helper://` URL protocol. Read README's "Turning the helper on and off from the app" before touching it. Five rules. **The registered command must never contain `%1`**: Windows only appends the clicked URL as an argument when the command asks for it, so its absence is the entire reason an arbitrary web page can't pass arguments to a program on the machine — this is the security property of the feature, not a detail. `/shutdown` **replies before scheduling the exit** (and defers it a tick), or the socket dies mid-reply and the page reports a failure for an action that succeeded. The control renders into every **`[data-helper-slot]`** on the page (Settings, the Shop Tracker's ⓘ dialog, and the TFT live-lobby card header), because the helper being down is noticed in all three — the buttons therefore carry **`data-helper-power`, never an id**, and the clicks are delegated from `document` once, since three copies of one id is invalid markup and slots are rebuilt on every repaint. `data-helper-mode="start-only"` slots render nothing while the helper is up: the game panels want a way in, not a Stop button in their header. In Settings the slot sits **outside `#valLocalCredsPanel`**, which hides itself when the helper is down — which is exactly when Start is needed. `waitForHelper()` is bounded by **wall-clock, not by a probe count**, because a fetch to a dead port costs Chrome ~2s and a fixed try count stretched "Starting…" to ~24s; and because that window can still be outlasted by a browser permission prompt, `renderValHelperPower()` **retracts the "nothing started" note whenever the helper is connected**, so a late success self-corrects. Finally `renderValHelperPower()` is called from `renderValLocalPanel()`, not only from `pollValLocalStatus()` — the token lives in `state`, which is still loading on first paint, and gating Stop on it left the button wrongly disabled for a full 15s poll cycle.
- **`notes.js` is the one tree in the app.** `state.notes` is a *flat* array; nesting is a `parentId` link and sibling order is the array's own order, so moving a subtree relocates exactly one record and its descendants follow. Three rules it depends on: the title `<input>` is live and its `input` handler must never call `renderNotes()` (that would rebuild the field mid-keystroke and drop the caret — `debouncedSaveNotes()` only); user text is assigned via `.value`, never interpolated into a `value="…"` attribute, because `escapeHtml()` does **not** escape double quotes; and `repairNoteTree()` runs at the top of every render, because a dangling or cyclic `parentId` makes a note unreachable from the roots and therefore invisible, which reads as data loss.
- **Notes rendering rules.** Clicking a row expands/collapses it and must *never* fall through to opening the text editor — folding the outline and starting to type are separate gestures (title field or ✎ button). Collapsing hides children **and** the body, which is what gives a childless note something to fold. Tags aren't stored: they're parsed out of the title by `noteTags()` on read, so renaming a note retags it and nothing can go stale. `renderMarkdown()` is hand-rolled (no bundler here) and is safe only because `escapeHtml()` runs on the whole source **first** — every rule after that operates on escaped text and emits only its own tags; link hrefs are additionally quote-stripped and scheme-checked against `MD_SAFE_URL`. Don't add a rule that interpolates source text into an attribute.
- **The scratch page is a hidden easter egg — the ENTRANCE is, at least** (`js/scratch.js`, `#scratchOverlay` in `index.html`). A small stack of free-form **pages** — no files, no tree, no typed titles — opened *only* by clicking the sidebar `.brand` logo, and paged through by swipe (touch), **hold Tab + scroll** (desktop), or the dots — the wheel needs all three of its rules (immediate first step, distance accumulation, and a cadence FLOOR), each of which was added because omitting it killed one scroll style; don't collapse them.  **Do not "fix" the missing affordance on the way in**: `.brand` deliberately has no `cursor:pointer`, no hover state, no `title`, no nav item, no Settings entry, and nothing in `renderAll()` calls into this file. The way *out* is the opposite and is meant to look clickable — `#scratchBrand` redraws the logo on top of the takeover (which would otherwise cover the very logo you clicked) from `.brand`'s live rect on every open, copying the icon box and font-size too because the mobile bar shrinks both on scroll; delete it and "click the logo again to exit" becomes dead code. Four more things are load-bearing. It is a **mode, not a tab** — it never touches `.nav-item.active` / `.view.active`, because routing it through nav.js's click ladder would re-run every tab's teardown/setup (resetting `goalFilter`, snapping Finance to `accounts`, stopping the Live Match poll) and a napkin must not have side effects on nine other tabs; the tab underneath stays rendered and is revealed again on exit. It must stay a **body-level sibling** of `.main`, never inside a `.view`, for the same reason `#valItemPreviewOverlay` sits outside `#view-games` — `.view{display:none}` would hide it whenever its host tab wasn't active, and it has to cover the sidebar. The click handler must keep ignoring `#navRightGroup`, which holds the ▶ Play button and sits *inside* `.brand` below 760px. And `z-index:950` is chosen against the ladder: above the mobile sidebar (40) and the tab-switcher FAB (900, or a violet button floats over an otherwise-bare page), below the 1000 modal tier — modal beats mode.
- **Scratch pages: flat array, addressed by id, never empty** (`ensureScratchPages()` in `js/scratch.js`). `state.scratch = { pages:[{id,html,updatedAt}], activeId, updatedAt }`. The current page is keyed by **id, not index**, so a page deleted in another tab can't silently leave you standing on different content; `ensureScratchPages()` is the single invariant enforcer (array exists, holds ≥1 page, `activeId` resolves) and is cheap and idempotent, so call it from anywhere that just changed the array. Four rules. The surface is the live copy of whichever page is showing, so **anything that changes which page that is must call `commitScratchSurface()` first** or the edit is lost on switch — that's why `scratchGoTo`, `addScratchPage`, `deleteScratchPage` and `closeScratch` all open with it. **Nothing auto-focuses the writing surface on a coarse pointer** (`scratchWantsAutoFocus()`): on touch, opening the pad, changing page, or tidying the dot row must never raise the soft keyboard — it covers half the screen, and flipping through pages is a reading action. The surface is contenteditable, so tapping it raises the keyboard natively at the only moment that's wanted. Two deliberate exceptions: `scratchGoTo()` keeps focus if you were *already* typing (so a swipe mid-sentence doesn't drop the keyboard, and the caret stays valid across the innerHTML swap), and `addScratchPage()` focuses unconditionally because asking for a BLANK page is an explicit intent to write. On a fine pointer everything focuses as before. Reordering is a pointer-event drag on the dots, and its one non-obvious requirement is that **pointer capture goes on the ROW, never on the dragged dot** — each crossing re-renders the row's innerHTML, so capturing the dot would release it the instant that node was replaced and the drag would die after a single step; the row element survives every re-render. Pointer events rather than the HTML5 drag-and-drop `notes.js` uses, because that API never fires on touch. Page names are **derived on read** from the first line (`scratchPageTitle()`, the same never-goes-stale trick as `noteTags()`); it walks top-level children rather than splitting `textContent` on `
`, because `textContent` concatenates blocks with no separator (`<div>a</div><div>b</div>` is `"ab"`). **The stack always ends in a blank page** (`ensureTrailingBlankScratchPage()`), so a new note is reached by paging past the last one rather than by pressing `+` — which is why that button now navigates to the waiting sheet instead of stacking a second empty one. It is kept out of `ensureScratchPages()` on purpose: that one is called from read paths too (`scratchActivePage()`, `serializeScratch()`, the search index), and a read that silently grew the array would leave the dot row describing a stack that no longer exists. Writing on the last page grows the next one behind it, gated on a cheap live-surface blankness test so the parser runs once per sheet rather than once per keystroke. Extra trailing blanks are swept on close down to **exactly one** — never while you type, since the dot row shifting mid-gesture is worse than a spare dot — and a blank page in the middle was still put there on purpose and is left alone. The page-turn click reuses **js/checklists.js's** `sfxTone()`/`sfxOutput()` — never open a second `AudioContext` for it, for the reason already recorded in `js/goals.js`: a second context means a second output bus, which is exactly what the compressor over there exists to prevent. It's muteable from the tool bar — **the dots and the tools are two rows, not one** (renderScratchPages() fills #scratchPages, renderScratchTools() fills #scratchTools in the footer strip); don’t merge them back, because on a phone eight dots plus five buttons overflow a 360px line, the row wrapped, and the page indicator stopped reading as one. Both containers share the onScratchRowClick delegate; only #scratchPages carries the reorder pointer handlers, which is why the drag maths can still assume every child is a dot. Mute rides (`state.scratch.mute`) rather than from Settings, which would hand the easter egg a visible entry. And the Tab chord swallows Tab while the page is open, replaying it as a focus move only if it's released *unused*, with a `window` blur reset — without that an alt-tab away eats the keyup and the modifier sticks down for good.
- **The scratch surface is `contenteditable`, so `sanitizeScratchHtml()` is not optional** (`js/scratch.js`). It holds tickboxes, links and pasted images, which a `<textarea>` cannot — and the HTML round-trips through the same unauthenticated shared row as everything else, so it is untrusted on the way back in. The sanitizer **rebuilds** against an allowlist rather than filtering: parsing goes through `DOMParser` (inert — nothing loads, nothing executes, no `onerror` fires while it's inspected), unknown tags are *unwrapped* (`<marquee>hi</marquee>` → `hi`), `SCRATCH_DROP` tags are discarded *subtree and all* (a `<style>` unwrapped would paste a stylesheet's source into your napkin), and no attribute survives unless it is re-validated — `href`/`src` against `SCRATCH_SAFE_URL` / `SCRATCH_SAFE_IMG`. It runs at exactly two boundaries, in (`applyLoadedScratchState`) and out (`serializeScratch`); live typing writes raw `innerHTML` into state, which is safe because it *is* the live DOM, and sanitizing per keystroke would only fight the caret. Three related rules: pasted images go through `uploadCompressedImage()` and only their **URL** lands in the page (CLAUDE.md's image convention, and this page is re-uploaded *whole* on every debounce fire — an inlined photo would be re-sent every 1.5s while you typed); a tickbox toggle must write the `checked` **attribute**, not just the `.checked` property, because only the attribute survives `innerHTML` serialization and the property alone looks right until the next reload; and `syncScratchSurface()` is the only thing allowed to assign the surface's `innerHTML`, for the same caret reason the Notes title input has. **Images are click-to-open and hover/long-press-to-resize**, and the split matters: clicking an `<img>` opens the body-level `#scratchImgOverlay` studio (see the next bullet; body-level for the `#valItemPreviewOverlay` reason — `#scratchOverlay` carries `z-index:950` and so creates a stacking context a child could never escape to reach the 1000 modal tier), while the resize outline and grip are `#scratchImgBox`, a sibling of `#scratchText` rather than anything inside it — no selection class on the image, no handle element in the editable, because the surface's `innerHTML` is the saved document. The only thing a resize writes is the image's own `width` **attribute** (`<font size>`'s reasoning again: one integer, one regex, no CSS parser), never a height — `height:auto` in the CSS is what keeps the aspect ratio, and `max-width:100%` clamps the display on a narrow screen so a width set on a laptop is remembered rather than lost. `enableObjectResizing` is switched off in `openScratch()` or Firefox draws its own competing handles. The box **re-reads the image rect every frame** (`trackScratchImgBox()`) rather than repositioning on scroll/resize events — don’t “optimise” that back into event hooks: `animateScratchPage()` runs a 180ms `translateX` on the surface, so hovering an image mid-page-turn measured it 20px from where it would land, and a CSS animation ending fires neither event, so the outline stayed wrong until the pointer left and came back. The loop runs only while an image is hovered and stops itself when the box goes. **An image can also be lifted OUT of the text flow to overlap the writing and the other photos** — dragging an inline image lifts it and moves it in one gesture (long-press first on touch), the `#scratchImgLift` button on the box is the discoverable way in and the only way back, and a file *dropped* on the sheet arrives already floating at the drop point while a *paste* still lands inline at the caret (the clipboard carries no position). Five rules. The position is **three data attributes** (`data-x` percent of the sheet width, `data-y` px, `data-z` order), validated in the sanitizer exactly like `width` and for the same reason — the `left`/`top`/`z-index` the browser lays out from are written by `layoutScratchFloats()` and are deliberately **not** in `SCRATCH_STYLE_OK`, so they're stripped on the way out and re-derived on the way in; putting `position`/`left`/`top` in the style allowlist instead would let anything arriving from the shared unauthenticated row cover the page with itself. x is a **percentage** and y is **pixels** because the 70ch column reflows between a laptop and a phone but the paragraph a photo was placed beside does not, which is why anything that re-measures the sheet (page switch, load, resize, an image finishing its download) has to call `layoutScratchFloats()` again. A float is a **child of the surface**, not of the paragraph it came from, so editing a sentence can't delete a photo you positioned by hand. `.scratch-text` carries **`position:relative` *and* `isolation:isolate`** — the first makes it the containing block (so floats scroll with the content and extend its scroll height), the second keeps `data-z`'s 0–999 from competing with the resize outline (2) and the find panel (3). And floats get **no background and no `border-radius`**, because a cut-out PNG has to composite against what's underneath it; the other half of that promise is `js/core.js`, which no longer re-encodes an image carrying alpha as a JPEG.
- **Clicking a scratch image opens the studio, which is a lightbox that can also crop and cut out** (`openScratchImgView()` in `js/scratch.js`, `#scratchImgOverlay`). It stays a lightbox at rest — seeing a photo bigger is the common act and is still one click — and every edit is **non-destructive until Save**, which **uploads a new file rather than overwriting the old one**: `uploadCompressedImage()` gives each image its own `uid()` path, so an edit leaves the previous URL referenced by no page and the reclaim sweep already running in `closeScratch()` (`sweepDeletedScratchImages()`) collects it — no delete call anywhere in the studio, and Ctrl+Z still works until the pad shuts. The rules that hold it up. The picture is drawn into a **`<canvas>`, not the `<img>`**, because the Edge slider recomputes the whole cut-out per tick and an encode + object URL per tick would cost more than the cut-out; the `<img>` survives for exactly one case, a photo whose bytes can't be read back — the source is fetched a **second time with `crossOrigin`** (the taint is on the canvas, not the request, so there is no test but to try) and a failure degrades to view-only rather than to a button that throws. State is **three layers and the order is the design**: `orig` never changes (Reset returns to it), `base` is what crops made of it, and the cut-out is a **live recomputation over `base`, cached on `out`, which every mutation clears** — so nothing has to remember to re-run the fill, only to forget the answer. **Only a crop bakes**, and it has to: a live cut-out's seeds are the old border ring, which the crop has just thrown away; baking keeps the picture you were looking at and the button re-runs on the new edges for free, because an already-transparent pixel seeds the next fill. Crop geometry is **fractions of the picture end to end** — `.scratch-imgview-frame` shrink-wraps the display element so the layer's percentages *are* the image's coordinates, which is what spares the whole crop UI from measuring a letterboxed `object-fit` box on every resize — and pointer capture goes on the **layer, never a handle**, the scratch dot row's rule. Background removal is a **flood fill inwards from the edges**, and that is deliberately the honest limit: it lifts a subject off a plain background and will not segment a person out of a street scene, since no model ships in a repo with no build step. A flood rather than "delete every pixel this colour" is what keeps a white shirt on a white wall, and each pixel is compared against **the colour of the seed its region grew from**, never its neighbour — comparing to the neighbour walks a gradient clean across the subject one imperceptible step at a time. A rejected pixel is **not** marked visited, which is what lets a hand-picked colour claim it later. The boundary pass (partial alpha from colour distance, then un-blending `c = (c - bg(1-a))/a`) is not polish: a hard mask leaves a one-pixel fringe of the old background all the way round, and that halo is what makes a cut-out look cut out. Save always hands **PNG** to `uploadCompressedImage()` and lets *it* choose the stored format — a crop comes back a JPEG, a cut-out keeps its alpha (`js/core.js`) — and the `width` **attribute is scaled by how much of the picture survived**, measured against `studio.orig` rather than `naturalWidth` so it stays right where the working copy was downscaled; nothing is written where there was no width, because that image is being laid out by the column. `closeScratchImgView(force)` prompts before discarding, and `force` exists for the one caller that can't be refused — `closeScratch()` is already tearing the pad down, and a prompt there would leave the studio over a page that had gone.
- **Persistence** (`js/persistence.js`): inside Claude.ai uses `window.storage`; deployed elsewhere falls back to Supabase, writing to a shared unauthenticated row (`app_data`, `id='shared'`) with optimistic-concurrency conflict detection and a localStorage offline cache. **Jobs, Notes and the scratch page are the exceptions** — each persists to its own resource (`id='jobs'` via `js/jobs.js`, `id='notes'` via `js/notes.js`, `id='scratch'` via `js/scratch.js`); see "Data safety" below. Read README's "Persistence — two modes, no auth" section before touching load/save logic.
- **Valorant tooling is intentionally local-only** (`scripts/valorant-*.mjs`, run on the user's own machine, not as a cloud/Edge Function) — this is a deliberate anti-fraud-detection workaround documented at length in the README ("Daily Valorant store check", "Getting the initial session"). Don't try to "fix" this by moving it back to a cloud function.
- **"Log in with browser" automates the cookie *copy*, never the login** (`scripts/valorant-login-window.mjs`, `POST /login-window` + `-status` + `-cancel`, the 🌐 button inside the Add-account / Re-login dialog). It is **opt-in, not the default path**: 🔑 Re-login on a store banner opens that dialog locked to the account so the cookies can be pasted, and only the 🌐 button in it opens a window — don't wire a fix-this-session control straight to `startValLoginWindow()`. It launches the user's **default browser** (Windows `https` handler out of the registry; falls back to Chrome/Brave/Edge, `VALORANT_LOGIN_BROWSER` overrides, Chromium-family only since the read is CDP) with `--app=` and a fresh `--user-data-dir`, the human signs in there, and the `ssid` is lifted out of that window's own cookie jar. **The script is standalone** — `node scripts/valorant-login-window.mjs [label]` (or the `.cmd`) rewrites `.valorant-session.json` with no server, no app and no tab involved; the helper's three routes are a second front door for the buttons, so don't refactor the flow as though the server owned it. This does **not** reopen the Puppeteer question the README settles — that ruling is about a *driver* working the login form, which nothing here does. The rules that keep it on the right side of the line: **no anti-detection flag may ever be added to that argv** (no `--enable-automation` to counteract, no `--disable-blink-features=AutomationControlled`, no UA override — the moment it needs to disguise the window, the answer is the manual paste, which is why that path stays); the cookie read is `Storage.getCookies` on the **browser** target only, never attaching to the page or enabling a domain on it, so nothing observable from Riot's page changes; and the throwaway profile is wiped on every terminal state, because it holds a live Riot session. It's a job with polling, not a blocking request, because a sign-in takes minutes — hence `/status` reporting an in-flight window, which is what lets a reloaded page adopt one instead of offering to open a second.
- **A saved Riot session is a cookie *jar*, not an `ssid`** (`sessionCookieHeader()` / `silentReauth()` in `scripts/valorant-lib.mjs`; README's "A session is sometimes two cookies" has the full finding). `clid` is a 3-char auth-cluster code — omitting it routes the reauth to Riot's default cluster, which works for *some* accounts and returns `303 -> authenticate.riotgames.com/login` for the rest, and that bounce is byte-for-byte the expired-session response. So a missing `clid` presents as a permanent false "session expired" that re-pasting the `ssid` never fixes. Four standing rules. `silentReauth()` takes the **session record**, never a bare cookie string, and every ladder entry point (`checkAccountStore`, `checkAccountOwnedSkins`, `ensureLiveAuth`/`getLiveMatch`) threads that record through — don't "simplify" any of them back to `sessions[label].ssid`, which is what made the bug possible. `loginAccount()` stores **whatever cookies it was handed**, so a new Riot requirement needs no code change, and `valorant-login-window.mjs` captures the whole `riotgames.com` jar for that reason. `clid` is **validated and not discoverable** — every wrong code is rejected, and an unauthenticated request always returns `as1` — so don't add a cluster-guessing fallback; the value is one field away on the same DevTools screen, which is why the Add-account dialog asks for it only after Riot refuses the `ssid` alone. And "session **incomplete**" must stay distinct from "expired": the wording is load-bearing, since `js/valorant.js` matches `/expired|invalid|incomplete/i` to offer 🔑 Re-login. `tdid`/`csid` were tested and are not required.
- **An account label is a primary key in five places, so renaming is a migration** (`commitValAcctRename()` in `js/valorant.js`, `POST /rename-account` + `renameStoreSnapshot()` on the helper side). The label keys the helper's `.valorant-session.json`, the widget's `.valorant-latest-store.json`, and `dailyStores` / `ownedSkins` / `wishlist` in the shared row — plus `live.label`, which pins an account for Live Match, and `selectedStoreLabel`. The helper owns the two files and the page owns the rest; **the page must mutate its state only after the helper has returned ok**, so a failed rename leaves both halves agreeing on the old name instead of splitting a session from its data. Add a new per-account bucket to `state.valorant` and it has to join that migration list, or renaming silently orphans it (which is what the stale wishlist keys in existing data are).
- **The Shop Tracker's account switcher is chips, not a `<select>`** (`renderValAcctSwitcher()`). `valSelectedLabel()` is the single reader of the current choice and falls back to "All" for a label that no longer exists — the old `<select>` was the source of truth for Settings' Check/Delete buttons too, with state merely mirroring it, so don't reintroduce a DOM element as the authority. The chips carry the same ★/⚠ signals as the nav badge, which is why `updateValWishlistBadge()` re-renders them.
- **The Live Match panel is memory-only by design** (`scripts/valorant-live.mjs` + `POST /live` on the local server + `renderValLive()` in `valorant.js`). No Supabase RPC, no shared-blob write, no snapshot file — `state.valorant.live` holds *preferences* only, and the lobby is thrown away. Don't add a write path: it polls every few seconds, so persisting it would re-upload the whole shared blob continuously to store data that's stale within minutes. Three related rules: `ensureLiveAuth()` caches the Riot token for 45 minutes and is the **only** place in the repo that may do so (the store/inventory checks keep their own from-scratch ladders — see the comment above it); the per-lobby data is memoized against the match id because a coregame roster can't change, so don't "simplify" that into a refetch-per-poll; and `lastLobby` is kept *on purpose* after a match ends (phase `'ended'`, with the final scoreboard resolved from `match-details`) so the panel doesn't blank the moment you finish a game — don't "clean it up" on presence 404, and note that `'ended'` must never hold the auto-account rotation lock (`isLivePhase()`), or the next match is never noticed.
- **The desktop widget** (`scripts/valorant-widget.ps1`, WinForms via PowerShell — the "no build step" rule applies to it too, so don't propose Electron/Tauri) renders from `scripts/.valorant-latest-store.json` **only**, never from Supabase. That file is written by `writeStoreSnapshot()` in `valorant-lib.mjs`, called from `recordAccountResult()`/`recordAccountError()`, so it stays current no matter which entry point ran the check. Anything new that records a store result must go through those two functions or the widget silently keeps showing yesterday's store. Note `recordAccountResult()` writes the snapshot *before* the Supabase RPC on purpose — a Supabase outage shouldn't blank the widget.

## Working conventions

- Images (goal/finance icons, fitness progress photos) are stored as Supabase Storage / Google Drive URLs in `state`, never as embedded base64 — keep new image-handling code consistent with that (`uploadCompressedImage()` in `core.js`).
- **`uploadCompressedImage()` picks its output format from the pixels, not from the caller.** It downscales and re-encodes as JPEG as it always did, *except* when the source type can carry alpha (`ALPHA_SOURCE_TYPE`) **and** a scan of the already-downscaled canvas finds a pixel that isn't fully opaque — then it emits lossless PNG, and the upload's path extension and `contentType` follow the blob's type. JPEG has no alpha channel, so the old unconditional path flattened every transparent PNG onto black. Don't "simplify" this back to trusting `file.type`: nearly every pasted screenshot is `image/png` and fully opaque, and encoding those losslessly would multiply what Storage holds for nothing. The scan early-exits on the first transparent pixel, so the full walk only ever costs an opaque PNG.
- New fields on `state` get defaults added in `persistence.js:applyLoadedState()` so old saved data upgrades in place — this repo does not use migration scripts. **Two exceptions:** new *job-record* fields go in `jobs.js:applyLoadedJobsState()` and new *note-record* fields in `notes.js:applyLoadedNotesState()` instead (see below). Everything else, including `state.jobSiteAccounts`, still belongs in `applyLoadedState()`.
- Adding a whole new top-level `state` key needs no change to `doSave()` — the rest-destructure carries it automatically.
- Gitignored local secrets: `scripts/.valorant-session.json`, `scripts/.valorant-local-token.json`, `scripts/.valorant-notify-config.json`, and the `scripts/.valorant-login-profile/` browser profile — never commit these or print their contents.

## Data safety — do / don't

Two tabs persist to their **own** resource instead of the shared blob:

| Tab | Row id | `window.storage` key | Owner file — save / load / hydrate |
|---|---|---|---|
| Jobs | `jobs` | `app-data-jobs` | `js/jobs.js` — `saveJobs()` / `loadJobsData()` / `applyLoadedJobsState()` |
| Notes | `notes` | `app-data-notes` | `js/notes.js` — `saveNotes()` / `loadNotesData()` / `applyLoadedNotesState()` |
| Scratch | `scratch` | `app-data-scratch` | `js/scratch.js` — `saveScratch()` / `loadScratchData()` / `applyLoadedScratchState()` |

Each mirrors `persistence.js`'s safety properties (own `loadedOk`-style gate, conflict detection, offline cache, serialized save chain) and has its own scoped conflict/offline banners rather than the global ones. Rationale: the shared blob is re-serialized and re-uploaded *in full* on every save from *any* tab, so a long application list — or a whole notes outline — would be re-sent on every unrelated edit. Notes is the sharper case: it debounce-saves per keystroke, so in the blob every paragraph typed would re-upload every goal, habit and finance record in the app.

**Never — each of these loses data silently, with no error:**
- Call plain `save()` after mutating `state.jobs`, `state.notes` or `state.scratch`. It won't persist; the edit vanishes on reload. Use `saveJobs()` / `saveNotes()` / `saveScratch()` (`debouncedSaveNotes()` / `debouncedSaveScratch()` for per-keystroke fields). Conversely, `state.jobSiteAccounts` stays on `save()` — it deliberately remains in the shared blob.
- Re-add `state.jobs`, `state.notes` or `state.scratch` hydration to `applyLoadedState()` — it would overwrite the dedicated row with a stale shared-blob copy.
- Replace `const { jobs, notes, scratch, ...mainState } = state` in `doSave()` with a hand-written key list. A jsonb write **replaces** the column rather than merging, so any key missing from that object is destroyed on the next save from any tab.
- Serialize `state.notes` anywhere except `notes.js:serializeNotes()`, or `state.scratch` anywhere except `scratch.js:serializeScratch()` — the latter is also the outbound sanitizer boundary, so bypassing it persists unsanitized HTML. It's the wire format, and it deliberately omits fields sitting at their default (~45% smaller); `applyLoadedNotesState()` restores them on the way back in. Writing raw `state.notes` isn't wrong, just wasteful — but *reading* a compact record without going through the hydrator is, since `parentId`/`body` will be `undefined`.
- Remove the standing migration in `loadJobsData()` / `loadNotesData()` (seeds the dedicated resource from a pre-split embedded copy whenever it finds the row absent). It is not a run-once script — any browser/device that hasn't loaded the current code yet still depends on it. **`loadScratchData()` deliberately has no such migration and takes no `parsedMainState`** — `state.scratch` has never existed in any shipped build, so there is no pre-split copy to rescue; don't add a branch "to match the others", because this rule would then keep code alive that can never fire.
- Add a row to `scripts/backup-supabase.sh` without also reading it out in `manage-backups/index.ts` **and** applying it in `backups.js:doRestore()`. A row that is backed up but never restored looks safe and isn't.
- Rename the row ids / storage keys (`shared`, `jobs`, `notes`, `scratch`, `app-data-jobs`, `app-data-notes`, `app-data-scratch`), or delete the `jobs`/`notes`/`scratch` rows as though they were strays.
- `git revert` past `e666ca9` without first copying the `jobs` row's contents back into `shared.data.jobs` — older code doesn't know the row exists.

**Requires a deploy step — editing the file alone does nothing:**
- Any `supabase/functions/*/index.ts` change → `npx supabase functions deploy <name>` (repo is already CLI-linked).
- Changing the backup file shape in `scripts/backup-supabase.sh` → redeploy `manage-backups` in the same sitting, or restores break. Backup files hold all four rows as `[{id,data},…]`; consumers must key off `.id`, **never** array position (rows come back id-ordered, so `jobs`, `notes` and `scratch` all precede `shared`). The `jobs`/`notes`/`scratch` rows may each legitimately be absent. Pre-split backups use the older `[{data}]` shape with no `id` key — every one of these shapes must keep working.

**Deliberate limits — don't "fix" these:**
- Site Accounts passwords sit in plaintext in the shared unauthenticated row; the masking is UI-only. A documented trade-off, not an oversight.
- Jobs auto-ghosting only flips `applied` → `ghosted` at 30 days, never `interviewing` — only one date is tracked, so it can't fairly judge a stalled interview.
